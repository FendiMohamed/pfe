Theme
- Minimal light academic theme.
- Background: white or very light gray.
- Text: charcoal.
- Accent: muted blue with limited muted teal for evidence highlights.
- Use simple tables, thin rules, clean diagrams, and real report screenshots.
- Do not use decorative gradients, playful visuals, or dense dashboard styling.
- Keep one main claim per slide.
- Do not use em dash punctuation.

Communication Job
By the end, the jury should understand that this work combines a research framework for trustworthy APK-derived SBOM claims with an implemented, evaluated engineering pipeline that recovers bounded, evidence-based SBOM and vulnerability information from compiled Android APKs.

Slide 8. An SBOM is a structured component inventory
Purpose: Define SBOM simply.
Visible content:
- SBOM means Software Bill of Materials.
- It records components, versions, identifiers, and relationships.
- Standards such as CycloneDX and SPDX define exchange formats.
- Package URL helps identify ecosystem package coordinates.

Speaker note summary:
The project uses CycloneDX and PURL because the output should be interoperable, not a custom detector report only.

Slide 9. Build-time SBOMs and reconstructed SBOMs are different
Purpose: Establish key conceptual distinction.
Visible content:
- Build-time SBOM: produced from source, dependency resolution, and build metadata.
- Reconstructed SBOM: inferred from the delivered artifact.
- The reconstructed case must preserve uncertainty and provenance.
Suggested visual:
- Split diagram with build-time path and APK-recovery path.
Speaker note summary:
A build-time SBOM has access to authoritative metadata. A reconstructed APK SBOM must infer from residue and should never claim more authority than the evidence supports.

Slide 10. Android builds transform the evidence before analysis
Purpose: Explain the Android build path.
Visible content:

- Java and Kotlin code becomes JVM bytecode.
- D8 converts bytecode into DEX.
- R8 may shrink, optimize, obfuscate, and inline code.
- The result is a signed APK.
Suggested visual:
- Linear Android build pipeline from source to signed APK.
Speaker note summary:
This slide explains why dependency boundaries are not preserved in the final artifact. The analyzer sees the result of the build, not the developer's dependency graph.
