# Hybrid Matcher Router V1

Generated by `apk-sbom hybrid-matcher-router` or `scripts/build_hybrid_matcher_router.py`.

This is a report-only matcher-improvement planner. It compares the current matcher with tool-family strategies from the literature, routes current hard rows to scoped experimental profiles, and keeps default matcher/SBOM/CVE behavior unchanged.

## Guardrails

- This router is an experiment planner, not matcher scoring.
- No router recommendation changes selected versions, SBOM components, vulnerability labels, or source-validation metrics.
- Any future promotion must pass controlled, clean-real, partial-real, no-Maven, boundary, and CVE-sensitive controls.
- AI recommendations may influence triage priority and wording only.

## Current Matcher

- Weighted explainable matcher using package, class, method, opcode, dependency, literal, version-unique, optional API, and optional opcode-ngram evidence.
- Safe boundary: Current matcher remains the SBOM authority until a scoped strategy passes controls.
- Known gap: Fixed global weights are less effective for mixed APK conditions such as R8 shrink/inline, version-band ties, alias boundaries, and missing reference rows.

## Tool Strategy Comparison

| Tool family | Method | Pros | Cons | Router adoption |
|---|---|---|---|---|
| LibScout-style | Library profiles and structural hashes | Precise and explainable on clean known libraries. | Brittle under shrink, method inlining, and removed code. | Keep as baseline-weighted evidence and reference-profile completeness gate. |
| LibRadar/LibD-style | Package-independent clustering and opcode/graph-like similarity | More robust to simple obfuscation and scalable for identity. | Weak exact-version authority; nearby versions can collapse. | Use for coarse-to-fine recall, not final exact-version claims. |
| LibPecker/SAD-style | Class structural similarity and version-level comparison | Better aligned with exact-version recovery than package names alone. | Adjacent AndroidX/Kotlin versions and R8 shrink remain risky. | Use for scoped version-band rerank experiments. |
| ORLIS-style | CFG/fuzzy hashing and control-flow similarity | Survives renaming and some structural edits. | Heavier and can false-match similar code. | Candidate for future R8 structural profile controls. |
| LibHunter/LibScan-style | Coarse-to-fine detection pipeline | Controls runtime and avoids broad expensive search. | First-stage filter mistakes can hide true positives. | Use for matcher-recall and large-DB pruning profiles. |
| ATVHunter-style | Vulnerability-oriented matching | Good for prioritizing security-relevant uncertain rows. | Not a complete SBOM or dependency recall method. | Use for review priority only, not vulnerability labels. |
| LibAttention-style | Learned code representations for obfuscation robustness | Promising for R8 identity-risk classification. | Needs larger independent corpus and is not exact Maven version authority. | Use as AI report-only triage and future raw-code DL research. |
| LibMD-style | Multi-scale SBOM/CVE fusion with confidence | Closest to the project goal: SBOM plus vulnerability-aware evidence. | Complex calibration and strict regression gates are required. | Use as the long-term hybrid fusion direction. |

## Strategy Catalog

| Profile | Best use | Research basis | Main risk | Promotion gate |
|---|---|---|---|---|
| `baseline-weighted-evidence` | Clean or high-evidence rows where package/class/method/literal evidence is coherent. | LibScout-style profile matching plus local SBOM confidence design | Global weights struggle with R8 shrink/inline and adjacent version-band ties. | Already default; keep as control baseline for every experiment. |
| `coarse-to-fine-recall` | Source coordinate exists in the DB but was not emitted, or matcher score is below threshold. | LibHunter/LibScan coarse-to-fine filtering | A bad coarse filter can hide true libraries; must preserve full-family rescue checks. | Must improve matcher-recall rows without new clean/partial/boundary regressions. |
| `r8-structural-recall` | Opcode/dependency evidence is strong while package/class/method evidence is weak. | LibAttention, LibHunter, LibMD multi-scale and learned-code evidence | Global structural weights already caused regressions; use only scoped controls. | Controlled R8, clean-real, partial-real, boundary, and no-Maven controls must all stay clean. |
| `version-band-rerank` | AndroidX/Kotlin/nearby-version rows with tiny score gaps or source-known version drift. | SAD/LibPecker class-structural similarity and local version-unique evidence | Generic newer/older tie rules already regressed controls; must stay per-coordinate or per-family. | Target fixes plus zero selected-version/source-validation regressions in current controls. |
| `metadata-coherence-rerank` | Candidate versions differ mainly by dependency-era/POM support. | LibMD-style probabilistic SBOM evidence plus Maven dependency coherence | Unsafe if POM metadata is used alone; requires independently detected supporting coordinates. | Only activate when independent APK-side support confirms the candidate family/era. |
| `reference-growth-first` | The source coordinate/version is not represented by bytecode-bearing reference features. | LibScout/LibD reference-profile completeness requirement | Does not solve matcher recall by itself and can enlarge the candidate search space. | Recovered artifacts must be bytecode-bearing and evaluated before shared DB promotion. |
| `alias-boundary-map` | Public/source coordinates map to Android target, KMP, sibling, or relocated bytecode artifacts. | LibMD-style SBOM normalization and artifact-family handling | Can become misleading if aliases are counted as exact emitted components. | Report mapping only until alias pairs are validated as bytecode-equivalent. |
| `boundary-hash-only` | No APK bytecode is expected or static Maven versioning is not supported. | SBOM honesty for native/framework/protected/source-only payloads | Does not increase Maven recall or exact-version accuracy. | Never promote to exact Maven version without bytecode evidence. |
| `vulnerability-focused-review` | Rows involve CVE-sensitive ecosystems such as JSON, networking, crypto, XML, or logging. | ATVHunter-style vulnerability-oriented prioritization | Not a complete SBOM strategy and must not inflate CVE counts. | Can affect review priority only; CVE labels still require SBOM/source-validation evidence. |
| `ai-report-only-triage` | Hard R8/matcher-recall rows need prioritization or wording decisions. | Phase 6A RandomForest and Phase 6B Transformer prototype | Trained on project diagnostics, not independent ground truth for all APKs. | AI can recommend triage/wording only; it cannot emit confirmed versions. |

## Recommended Hybrid Path

1. Keep the current weighted matcher as the control baseline.
2. Use this router to select a scoped experiment profile per hard row family.
3. Let AI recommend triage/priority, but keep deterministic promotion gates.
4. Promote only a narrow profile that improves target rows and passes controlled, clean-real, partial-real, no-Maven, boundary, and CVE-sensitive controls.
