\chapter{Reproducibility and Evidence Index}
\label{app:pfe-reproducibility}

This appendix records the environment, command sequences, evidence classes,
and generated artifacts needed to reproduce or audit the principal results of
this thesis. It complements the conceptual and implementation descriptions in
Chapters~\ref{ch:pfe-design} and~\ref{ch:pfe-evaluation}.
The commands are written for the repository layout used during the final
evidence freeze of 20 June 2026. The corresponding Git base revision was
\texttt{2983d54}; thesis sources and generated documentation created after
that revision were present as an uncommitted working-tree layer.

The deterministic Python commands can also run in a Python 3.12 virtual
environment:

\begin{lstlisting}[style=thesiscode,

python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip

SDK installation. The optional extras \texttt{.[ml]} and \texttt{.[dl]} are
needed only to reproduce the machine-learning experiments discussed in
Chapter~\ref{ch:pfe-ai}.

\section{Core APK-to-SBOM Command Sequence}

\subsection{Stage-Level Inspection}

The following sequence separates archive inspection, DEX analysis, component
matching, and complete report generation. PowerShell variables are used only
to keep paths readable.

\begin{lstlisting}[style=thesiscode,
caption={Deterministic APK analysis and report workflow.}]
$apk = "data/test_apks/real/F-Droid.apk"
$db = "data/reference_db/reference_features_calibrated_combined.sqlite"
$out = "data/results/reproduction-fdroid"

docker compose run --rm apk-sbom python -m apk_sbom.cli inspect-apk $apk
docker compose run --rm apk-sbom python -m apk_sbom.cli analyze-dex $apk
docker compose run --rm apk-sbom python -m apk_sbom.cli match-apk $apk `
  --db-path $db --top 10 --min-score 0.05
docker compose run --rm apk-sbom python -m apk_sbom.cli generate-report $apk `
  --output-dir $out --db-path $db --top 30 --skip-osv
\end{lstlisting}

The stable shared database used by the ordinary lane is
\path{data/reference_db/reference_features_calibrated_combined.sqlite}.
The \texttt{--skip-osv} flag makes the run independent of the availability of
the OSV service. It does not disable extraction, matching, SBOM generation, or
the local report.

\section{Reference-Database Construction}

\subsection{Isolated Build Sequence}

Reference artifacts must be built in isolated paths unless a later promotion
gate explicitly authorizes their inclusion in the shared calibrated database.
A minimal isolated build is:

\begin{lstlisting}[style=thesiscode,
caption={Isolated reference-database construction.}]
$config = "configs/libraries.json"
$artifacts = "data/reference_db/artifacts_reproduction"
$dex = "data/reference_db/dex_reproduction"
$db = "data/reference_db/reference_features_reproduction.sqlite"

docker compose run --rm apk-sbom python -m apk_sbom.cli download-maven `
  --config $config --output-root $artifacts --dry-run
docker compose run --rm apk-sbom python -m apk_sbom.cli download-maven `
  --config $config --output-root $artifacts --quiet
docker compose run --rm apk-sbom python -m apk_sbom.cli convert-reference-dex `
  --artifact-root $artifacts --output-root $dex --quiet
docker compose run --rm apk-sbom python -m apk_sbom.cli `
  extract-reference-features --dex-root $dex --db-path $db --reset --quiet
\end{lstlisting}

The dry run exposes the planned Maven requests before network or disk work.
JAR files are converted directly; AAR files are unpacked and their bytecode is
converted to a common DEX representation. Feature extraction then writes
package, class, method, opcode, API-reference, graph, literal, and contextual
evidence to SQLite.

\subsection{Reset and Promotion Safety}

The \texttt{--reset} flag is destructive for the database path supplied to
the command. It is therefore valid only for a new or explicitly rebuildable
experiment database. Incremental batches omit \texttt{--reset}. An experiment
is not promoted merely because target rows improve: at least two affected
targets and clean, partial, no-Maven-signal, and boundary controls are checked
first. Any regression fails the promotion gate. This policy is why several
useful version and R8 experiments remain report-only or experiment-only.

\section{Source Validation and Vulnerability Enrichment}

OSV scanning can be run after an offline report:

\begin{lstlisting}[style=thesiscode,
caption={OSV enrichment and source validation.}]
docker compose run --rm apk-sbom python -m apk_sbom.cli scan-sbom-osv `
  "$out/sbom.cdx.json" --output "$out/osv-vulnerabilities.json"

docker compose run --rm apk-sbom python -m apk_sbom.cli validate-source-deps `
  --sbom "$out/sbom.cdx.json" `
  --dependency-tree "path/to/runtimeClasspath.txt" `
  --output-dir "$out/source-validation"
\end{lstlisting}

Source validation is an evaluation operation. It compares emitted Maven
coordinates and versions with a resolved Gradle dependency tree when source
is available. The dependency tree is not an input to normal APK matching.
Similarly, OSV can determine whether a supplied package version appears in an
affected range, but it cannot repair an uncertain or incorrect component
version. The report therefore preserves confirmed, potential, mismatch, and
report-only vulnerability classes.

\section{Reproduction Constraints}

Some operations depend on mutable external infrastructure. Maven downloads
can fail because an artifact moved, a legacy repository disappeared, or
Gradle metadata no longer resolves under a modern toolchain. OSV lookup
requires network access and can change as advisories are updated. Large
reference databases also make unconstrained matching materially slower than a
small demonstration database. For these reasons, generated JSON, source
dependency trees, proof bundles, decision ledgers, and dated evidence
snapshots are retained alongside commands.

Reproduction must also preserve the distinction between rerunning an existing
frozen artifact and recomputing it with current remote services. A different
OSV response, Maven repository state, or dependency-resolution result does not
retroactively change the thesis result; it creates a new dated observation
that must be reported separately. Finally, successful command execution does
not by itself authorize promotion. Shared-database, matcher, AI, and
vulnerability decisions remain subject to the target/control and evidence
boundaries defined in this thesis.
