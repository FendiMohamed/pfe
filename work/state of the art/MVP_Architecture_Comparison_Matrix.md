# MVP Architecture Comparison Matrix: Android APK SBOM Extraction

Scope: local papers in `ressources/papers` plus the serious internet-found papers and official tools previously collected.

Goal: choose an MVP architecture for extracting and identifying SBOM components from compiled Android APKs.

## Legend

| Tag | Meaning |
|---|---|
| P0 | Directly shapes the MVP architecture. |
| P1 | Important for evaluation, comparison, or later hardening. |
| P2 | Contextual or future-work value. |
| DEX | Java/Kotlin bytecode in `classes.dex` / multidex. |
| Native | `.so` libraries under `lib/<abi>/`. |
| Version | Can distinguish exact or near-exact library versions. |
| Obf | Handles at least some obfuscation, shrinking, or optimization. |
| SBOM | Useful for CycloneDX/SPDX output or vulnerability scanning. |

## Architecture Decision Summary

| MVP decision | Recommended choice | Main evidence |
|---|---|---|
| Overall architecture | Hybrid static pipeline, not one-feature matching. | LibScout, LibD, LibPecker, LibID, LibScan, LibHunter, SAD, and LibMD each show that one feature family fails under some combination of package renaming, dead-code elimination, R8, or small version differences. |
| First-stage extraction | APK unzip, parse all DEX files, resources, manifest, native `.so`, strings, certificates, and leaked metadata. | LibSift and LibRadar show the value of cheap structural/package/API clues; OSSPolice and LibRARIAN show that native and string evidence should not be ignored. |
| Code segmentation | Recover package/module candidates before expensive matching. | LibSift, LibD, LibRadar, and systematic assessment papers show that separating app code from TPL code is a core difficulty. |
| Candidate generation | Use cheap fingerprints first: package names if present, Android API-call profile, strings, resource/package clues, class count, method count, native symbols. | LibRadar, LibScout, OSSPolice, and cdxgen-style SBOM evidence favor explainable candidate narrowing before graph/CFG matching. |
| Robust DEX matching | Combine class dependency graph, method/opcode fingerprints, call-chain/opcode features, and CFG/basic-block signatures. | LibPecker, LibID, LibScan, ATVHunter, SAD, and LibMD are the strongest sources for this layer. |
| Version detection | Treat version detection as a separate scoring problem after library detection. | LibScout, IBM ICSE 2017, LibID, ATVHunter, LibScan, SAD, LibHunter, LibMD, OSSPolice, and AnchorDiff all show that library-level detection is not enough for vulnerability mapping. |
| Obfuscation strategy | Explicitly model obfuscation levels and report confidence. | ORLIS, LibID, LibHunter, LibAttention, LibMD, and ICSE 2026 robustness work show that R8 and advanced obfuscation can sharply reduce exact-version accuracy. |
| Native code | Make native `.so` matching a separate module, not an afterthought. | OSSPolice, LibRARIAN, DroidNative, DroidReach, and AnchorDiff show different feature needs for native code. |
| SBOM output | Emit CycloneDX JSON first, with PURL, hashes, evidence, confidence, APK location, and candidate alternatives. | CycloneDX, CISA SBOM Minimum Elements, Trivy, Grype, cdxgen, and Syft all favor machine-readable component identity and evidence. |
| Vulnerability scanning | Scan generated SBOM with Trivy/Grype and optionally enrich with NVD/Sonatype/OSV. | Trivy and Grype both support SBOM scanning; NVD and Sonatype provide vulnerability intelligence but require careful coordinate/version matching. |
| Evaluation | Measure library-level and version-level precision, recall, F1, false positives, runtime, and SBOM completeness under clear, ProGuard, R8, and Obfuscapk variants. | Automated TPL Detection, Systematic Assessment, LibHunter, Revisiting TPL Detection, and ICSE 2026 robustness study provide the most useful evaluation framing. |

## Recommended MVP Pipeline

| Stage | Inputs | Output | Adopted from | MVP note |
|---|---|---|---|---|
| 1. APK unpacking | APK file | Manifest, resources, all DEX files, native `.so`, certificates, strings | General APK tooling, OSSPolice, LibRARIAN | Preserve file paths for SBOM evidence. |
| 2. Metadata extraction | Manifest, resources, strings, native strings | Package clues, domains, Maven-like strings, version strings, hashes | LibRadar, OSSPolice, cdxgen, CISA | Cheap evidence helps explain matches. |
| 3. DEX parsing | DEX files | Classes, methods, packages, call edges, opcodes | LibScout, LibID, LibScan, ATVHunter, SAD | Avoid depending on decompiler correctness; parse bytecode-level structures. |
| 4. Segmentation | Classes/packages/call graph | App-code modules and candidate TPL modules | LibSift, LibD, Systematic Assessment | This reduces false positives before expensive version matching. |
| 5. Candidate generation | Module features + reference DB | Ranked candidate libraries | LibRadar, LibScout, OSSPolice | Fast filters: package hints, API profile, strings, class/method counts, hashes. |
| 6. Robust DEX matching | Candidate module + candidate reference versions | Library match, candidate versions, confidence | LibPecker, LibID, LibScan, SAD, ATVHunter, LibMD | Fuse CDG, class summaries, opcode, call-chain, CFG/basic-block features. |
| 7. Version scoring | Matched evidence across versions | Exact version, version range, or uncertain candidates | LibScout, IBM 2017, LibID, ATVHunter, SAD, LibHunter | Report uncertainty when adjacent versions are indistinguishable. |
| 8. Native matching | `.so` files per ABI | Native components, versions, confidence | OSSPolice, LibRARIAN, DroidNative, AnchorDiff | If time is limited, implement hashes + strings + symbols first and mark as phase 2. |
| 9. SBOM generation | Component decisions + evidence | CycloneDX JSON | CycloneDX, CISA, cdxgen, Syft | Include confidence and evidence properties, not just component names. |
| 10. Vulnerability scanning | CycloneDX SBOM | Vulnerability report | Trivy, Grype, NVD, OSS Index/Sonatype, OSV | Compare scanner output and explain false positives from uncertain coordinates. |

## Minimum Feature Set For A Defensible MVP

## Bottom-Line Architecture Choice

For the PFE MVP, choose this architecture:

`APK -> unpack -> extract DEX/native/resources/metadata -> segment likely TPL modules -> generate candidates from cheap metadata/API/string/package features -> run robust DEX matchers using CDG + class summaries + method opcodes + optional CFG/basic-block fingerprints -> score library and version confidence -> emit CycloneDX SBOM with evidence -> scan with Trivy/Grype and enrich with NVD/Sonatype/OSV.`

The thesis argument is simple: source-based SBOM tools are not enough for compiled APKs, while classic Android TPL detectors are not enough for SBOM because SBOM needs exact component identity, version, evidence, and scanner-compatible identifiers. The MVP should therefore connect Android TPL detection research with SBOM standards and vulnerability tooling.
